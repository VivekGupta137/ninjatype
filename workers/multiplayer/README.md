# Multiplayer backend

Implemented client: `/multiplayer-typing-race/`, linked from the site navigation and `/online/`. The legacy `/multiplayer/` route redirects while preserving invitation query parameters. WPM, accuracy and typing progress update locally. A compact top-five panel sits beside the keyboard on desktop and below it on mobile. Opponents' live estimates refresh about every three seconds; final scores replace estimates after the race. The Astro site stays static. This Worker owns the Room and Directory SQLite Durable Objects. Room sockets use hibernation; there are no keystroke uploads, server intervals, avatar API calls, accounts, or global room-count cap.

Progress reports contain only the round ID and correct-character count, at most once per aligned three-second window per player, including unchanged counts so pauses appear in the WPM trend. The room sends one compact standings broadcast per three-second window, triggered by incoming reports rather than a timer. Live counts and broadcast timestamps live in hibernatable socket attachments; they do not write authoritative room state or KV. Reports are bounded, limited to current connected participants, and never select a winner or populate final metrics. New spectators receive current estimates with their admission snapshot. The first broadcast in a window can include older reports from other players, so the panel is approximate. Deploy the Worker before the frontend; clients upload progress only when its config advertises `liveProgress`. The advertised `progressIntervalMs` keeps a new frontend compatible with an older ten-second Worker until it is updated.

Player avatars use the DiceBear Moods style, generated locally from a SHA-256 hash of each normalized nickname and held in a bounded client cache. The bundled Moods definition is CC0; rendering makes no avatar API requests.

The entry form keeps one Turnstile widget with the `room_entry` action while switching Create/Join tabs. A tab selection does not spend a token or reload the widget. Each submitted operation immediately consumes its client token. The existing widget resets after creation completes or a room connection fails; a successful connection removes it. This avoids loading a new challenge while admission is pending. Creation and subsequent room entry require separate successful checks. The Worker also accepts legacy operation-specific actions, so deploy it before the updated frontend.

Rooms support Words mode (15, 30 or 50 words, capped at two minutes) and Time mode (15, 30, 60 or 120 seconds). Both offer the existing English 1k, English 5k, English 2k short/long, English 5k medium and Brainrot lists. Settings are authoritative and preserved on rematch. Quote lists are excluded. Words mode ends on the first accepted completion; Time mode ends at the deadline and selects the highest correct-character score after everyone reports or the ten-second final-score window closes. Accuracy then stable participant ID break ties; zero input produces no winner. A timed round must fit its full duration and score collection before the room's hard expiry.

Time mode generates one shared passage on the Worker, sized above the accepted 1,000-WPM pace (roughly 1,270 / 2,520 / 5,020 / 10,020 characters for the four durations). It sends that passage once in the round snapshot; there are no mid-race text fetches. The browser renders at most 60 nearby words as the cursor advances. Final score payloads are bounded at 16,384 characters in Time mode.

When the race ends, the keyboard closes and the results show “Race over”, final standings, and an SVG chart for every racer with WPM/completion toggles. Trend samples stay in browser memory/session storage (at most 42 points per player for the current round), require no server history writes, and reset on rematch. Reconnecting browsers show their saved observations plus available live/final points; they cannot recover unobserved historical samples from the server.

## Run locally

1. From the repository root, run `cp workers/multiplayer/.dev.vars.example workers/multiplayer/.dev.vars`. The example uses Cloudflare's public always-pass Turnstile test keys; no dashboard secret is needed locally. `.dev.vars` is ignored by Git. These keys work only when both the request URL and browser origin are loopback addresses. Dummy responses have no real hostname/action and reuse their token, so local test admissions get separate receipts. Public requests still require hostname/action validation and normal replay protection.
2. Run `bun run dev:multiplayer` and `bun run dev` in separate terminals. Astro defaults to `127.0.0.1:4347` and fails clearly if the port is occupied. Keep one Astro process for this checkout; port 4321 may already belong to another app.
3. Visit `http://127.0.0.1:4347/multiplayer-typing-race/`. Vite forwards HTTP and WebSockets to port 8787, changes the upstream Host and preserves the browser Origin. Use `astro dev` for this workflow: `astro preview` serves the static build and does not run the dev proxy. If you choose another port, add that exact origin to `.dev.vars` and restart the Worker.

To play a local race, use a normal browser window and an incognito window at that same URL with different nicknames. In the first window, verify and create a room, then complete the fresh check and join that room. In the second window, verify and join using the exact room name. Both players select Ready up, then either starts the race. Test results and Rematch after a finish. Open a new window directly rather than duplicating a joined tab, which may copy its reconnect state.

The public test keys always pass, but the widget and Siteverify still need access to `challenges.cloudflare.com`. A frontend room request times out after 12 seconds; inspect the browser Network entry for `/api/multiplayer/rooms` and the Worker terminal if this happens. Use `bun run test:multiplayer` to test the backend without loading the browser widget; its runtime suite mocks Siteverify and exercises two-player rounds, results and rematches.

For real Turnstile testing, replace both local test keys with your managed widget's keys and allow the hostname used by your browser. Production keys belong in the Worker config and Cloudflare secret storage. Dashboard secrets do not populate local Wrangler automatically. Public Turnstile test keys are documented at https://developers.cloudflare.com/turnstile/troubleshooting/testing/.

Refresh reads a bounded page from the live directory and works locally without cron. Initial discovery uses the cached KV snapshot when available, or a short-lived cached live page before the first publication. The room-directory cron does not run automatically during local development; invoke the scheduled event with Wrangler's `--test-scheduled` option when testing publication. Production publishes every three minutes.

`bun run test:multiplayer` runs pure lifecycle tests and a real workerd/SQLite/WebSocket integration suite with mocked Siteverify. It needs Node and Bun, uses temporary storage, and does not access a Cloudflare account. `bun run check:multiplayer` checks the Worker and Pages forwarder. `bunx astro check` and `bun run build` check the site.

## Configure deployment

Set `MAX_PLAYERS_PER_ROOM` as a plaintext variable on **Workers & Pages → ninjatype-multiplayer → Settings → Variables and Secrets**, or in this Worker's `wrangler.jsonc` `vars`. It defaults to `10` and accepts whole numbers of at least `2`; missing/invalid values fall back to `10`. Locally, put it in this directory's `.dev.vars`. Keep the Wrangler value in sync with dashboard changes because a later Wrangler deployment uses the checked-in configuration. This is a Worker runtime setting; Pages needs no variable or rebuild for capacity changes.

New rooms capture this value at creation, persist it, and advertise it in their snapshots/public listings. Existing rooms retain their saved limit through rematches and hibernation. Older rooms without a stored capacity use `10`. Reserved reconnect seats count toward the configured limit. Increasing the value increases per-room message, memory and storage work; the previous Free-tier examples assumed ten players.

Keep the account on **Workers Free**. No command here changes your plan or permits paid overflow. Cloudflare's Free request/storage/duration limits still bound capacity; Turnstile and throttling reduce abuse but cannot guarantee unlimited traffic on a Free plan.

1. Create a KV namespace using `bunx wrangler kv namespace create ROOM_DIRECTORY --config workers/multiplayer/wrangler.jsonc`. Replace `REPLACE_WITH_FREE_KV_NAMESPACE_ID` in this directory's Wrangler config with its ID.
2. Create/configure your Turnstile widget for the production hostnames (`ninjatype.com`, `www.ninjatype.com`, and `ninjatype.pages.dev` as applicable). Set `TURNSTILE_SITE_KEY` in this Worker config. Store the secret with `bunx wrangler secret put TURNSTILE_SECRET_KEY --config workers/multiplayer/wrangler.jsonc`.
3. Review exact `ALLOWED_ORIGINS`, custom-domain routes, and rate-limiter namespace IDs. Use account-unique limiter namespace IDs if another Worker already uses these IDs. Preview URLs need explicit origin/hostname configuration; there is no wildcard preview trust.
4. Deploy this Worker first using `bun run deploy:multiplayer`. The default config keeps multiplayer disabled until the keys and dependencies are ready. The SQLite class migration creates the two object namespaces. This must precede deploying Pages because Pages binds the Worker by service name.
5. Set `MULTIPLAYER_ENABLED` to `true` and deploy the Worker after configuring Turnstile and KV. Build/deploy Pages through the existing workflow. The root Pages config includes the `MULTIPLAYER` service binding, and `functions/api/multiplayer/[[path]].ts` forwards requests on Pages-owned domains. `_routes.json` invokes Functions only for multiplayer requests so practice/static assets bypass dynamic compute. Custom-zone Worker routes handle the custom domain directly and avoid the forwarding hop.
6. Verify creation, a separate challenged join, invites, two-browser starts, reconnects, results and rematches on the deployed origin. Confirm that origin and token values do not appear in application token logs; the code never logs tokens or places them in URLs.

No infrastructure has been provisioned or deployed by this implementation. Live Turnstile/account-quota behavior needs the configured deployment; local tests mock challenge verification.

## Lifecycle and controls

- Nickname input or generated nickname; client-side DiceBear Moods avatars seeded by SHA-256 of the accepted, NFC-normalized username. Moods artwork is CC0; library code is MIT. The dependency packages contain their licenses. No avatars are persisted server-side.
- Turnstile on creation **and every socket entry**, including creator entry, public/exact-name joins and reconnects. Separate operations use separate tokens. Rematches reuse the admitted socket.
- Origin checks plus approximate location-scoped gateway limits: creation 1/minute/browser and 5/minute/IP; entry 12/minute/browser and 120/minute/IP; discovery 6/minute/browser and 120/minute/IP. Browser IDs and reconnect IDs are unsigned correlation values, not identity proof.
- Configurable member seats (default ten), including disconnected two-minute reservations. Late joiners wait for the next round. At actual start, the Room freezes its connected candidate roster.
- Three-second countdown; Words mode offers 15/30/50 words with a two-minute limit, and Time mode offers a 15/30/60/120-second timer. The first valid server-accepted finish ends a Words race; its timeout has no completed winner. Time races compare final scores at the deadline. Server recomputes displayed metrics from one final text/count payload, with bounds; it cannot prove human typing without keystroke streaming.
- Ten-second initial final-metric collection; two-minute results/rematch window. Two connected opt-ins automatically start the next countdown once initial collection closes. Non-opt-ins wait. Cancelled countdowns retain the prior scoreboard and results deadline. Each new round gets a new ID.
- Room lifetime is fixed at 20 minutes. Empty rooms get two minutes of reconnect grace, clipped by results/hard expiry. Rematches/reconnects do not extend clocks. Silent failures are detected when the server observes a socket closure; no application heartbeat runs while typing.
- Incoming commands limited to 10/10 seconds and syncs to 2/10 seconds; persistent command flooding closes the socket. Duplicate metrics do not rewrite results. Challenge/admission receipts prevent cached Siteverify retries from creating extra rooms/connections; a bounded per-room receipt store throttles connection churn without capping room creation globally.
- Cleanup closes sockets and removes playable state. A closed room retains only challenge replay receipts until their five-minute retry window expires, then `deleteAll()` clears storage. No scores or playable room remain in that short tombstone. This intentionally avoids discarding replay protection when a room closes early.
- Directory metadata uses SQL rows and one batched KV snapshot every three minutes, approximately 480 KV writes/day. Explicit refresh reads up to 21 current SQL rows for a 20-room page under the existing discovery limits, without writing KV. Initial discovery uses the cache; lists are hints and joins validate live room existence/epoch/capacity. Snapshot growth is not an admission cap; KV value/CPU limits eventually require directory partitioning at larger scale.
- Local run state lives in session storage for reconnects; acknowledged personal metrics go to existing local history. Reconnection requires a fresh challenge and an explicit retry, with at most three attempts per disconnect window. No automatic challenge/request loop runs.

## Maintenance

Set `MULTIPLAYER_ENABLED=false` and redeploy the Worker. New HTTP operations fail closed; room commands also enforce maintenance. Existing idle sockets receive closure when their next command runs (or their scheduled alarm expires the room), rather than consuming resources in a polling loop. The client offers practice when config, admission, acknowledgment or reconnection fails. Setting `PUBLIC_MULTIPLAYER_ENABLED=false` at the Astro build disables even the initial config request.

Turnstile outages block new entries, while existing connected rounds can continue. KV outages affect discovery; challenged exact-name joins can still work. The two-minute reconnect window can expire while a user completes a challenge. Free quota exhaustion returns an unavailable/fallback state; no runtime switches plans.
